## Context

Сейчас бот — одностраничный `bot.py` без состояния: сообщение пользователя уходит в DeepSeek с фиксированным промптом, ответ возвращается, данные нигде не сохраняются. Промпт обещает «записал: жим 80», но записи не существует. Начинаем с первого домена — тренировок. См. proposal.md (Why).

Проект: Python + aiogram + DeepSeek, без внешних хранилищ. Новый домен хранения поедет в `bot/history` (spec см. в change).

## Goals / Non-Goals

**Goals:**
- Реальное сохранение отчётов о тренировках с датой/временем и привязкой к пользователю.
- Минимум новых зависимостей (ноль — используем stdlib `sqlite3`).
- Разделить «память» (извлечение фактов) и «личность» (живой ответ), чтобы бот не выдумывал то, что не сохранил.
- Автоматическая инициализация хранилища при старте; `data/` вне git.

**Non-Goals:**
- Другие домены (еда, вес, вода, сон, привычки, самочувствие) — только заложим структуру, но таблиц для них не создаём.
- Отчёты/агрегаты по истории — появятся отдельным изменением.
- Команды просмотра своей истории пользователем.
- Деплой на сервер, сетевые БД, Docker.

## Decisions

### SQLite вместо JSON/лог-файлов
Выбор: `sqlite3` из стандартной библиотеки, один файл `data/lifekick.db`.
- Впереди минимум 6 доменов + отчёты со склейкой по дате (вес→тренд, сон→энергия) — это реляционная модель, JOIN и GROUP BY поверх JSONL пришлось бы писать руками.
- Ноль новых зависимостей, нечего ломать и деплоить.
- Транзакции защищают от гонок при параллельных сообщениях.
- Альтернатива «JSONL-файл на пользователя» отклонена: легче на старте, но требует миграции и не даёт запросов из коробки.

### Одна база на всех, разделение по `user_id`
Один файл БД с колонкой `user_id` вместо каталога БД на пользователя. Один файл — один бэкап, кросс-пользовательские выборки возможны, схему эволюционируем в одном месте. Telegram даёт `user_id` в каждом сообщении (`message.from_user.id`).

### Схема `workout_entries`
```
id           INTEGER PRIMARY KEY AUTOINCREMENT
user_id      INTEGER NOT NULL          -- message.from_user.id
performed_at TEXT NOT NULL             -- ISO 8601 UTC, когда тренировался
reported_at  TEXT NOT NULL             -- ISO 8601 UTC, когда написал боту
kind         TEXT                      -- 'силовая' | 'кардио' | ... (nullable)
details      TEXT                      -- свободное описание (nullable)
```
`duration` намеренно не добавляем (решение пользователя). Времена храним в UTC (ISO 8601), привязку к поясу пользователя решаем позже. `performed_at` «сегодня/вчера» вычисляет LLM-шаг извлечения относительно переданного ему текущего UTC-времени.

### Два вызова DeepSeek: извлечение + ответ
На пришедшее сообщение:
1. **Извлечение** — отдельный вызов с temperature≈0 и `response_format={"type":"json_object"}`: на входе текст + текущее UTC-время (+ user_id), на выходе JSON:
   ```json
   {"is_workout": true, "kind": "силовая", "details": "жим 80", "performed_at": "2026-09-21T15:00:00Z"}
   ```
   Если `is_workout` = true — пишем запись в БД. Пустые поля не выдумываются.
2. **Ответ** — существующий вызов с системным промптом и character'ом; формулировку не трогаем.

Так «память» не зависит от настроения и длины ответа, а ответ — от успеха сохранения. Альтернатива «одним вызовом и запомнить, и ответить» отклонена: производство стабильного JSON в духе «живого друга» ненадёжно, а связывание ответа с фактом сохранения усложняет fallback.

### Хранение и доступ к БД
- Путь к базе: `data/lifekick.db` (относительно корня проекта). `.gitignore` получает `data/`.
- Инициализация при старте: создать каталог `data/`, открыть соединение, `CREATE TABLE IF NOT EXISTS`.
- Соединение — одно на процесс, обёрнутое в `threading.Lock` для записи (aiogram обрабатывает сообщения конкурентно в event loop). `WAL` режим включаем, чтобы чтение не блокировалось записью (понадобится при добавлении отчётов).

### Новая структура кода (минимальная)
- `storage.py` — `init_db()`, `save_workout(user_id, performed_at, reported_at, kind, details)`.
- `bot.py` — в `ai_handler`: step 1 (извлечение) → при `is_workout` сохранение → step 2 (ответ). Парсинг JSON с fallback: не разобрали — не сохраняем, просто отвечаем (см. spec, сценарий «Извлечение не удалось»).
- `system_prompt.txt` — точечная правка: подтверждение «Записал…» теперь означает реальную запись; добавляем одну строку правил сохранения, не трогая характер.

## Risks / Trade-offs

- **LLM выдумает тренировку** → temperature=0, явный запрет выдумывать, JSON-режим, сохраняем только при `is_workout` и наличии текста подтверждения. Полный контроль вариантов невозможен, но цена ошибки — одна лишняя строка в личной базе.
- **Неправильный `performed_at` из-за часового пояса** → на старте передаём в извлечение актуальное UTC; пояса пользователей — открытый вопрос ниже. На точность отчётов повлияет позже.
- **DeepSeek вернёт невалидный JSON** → парсим с try/except; при ошибке сообщение не сохраняется, пользователь получает обычный ответ без упоминания записи.
- **Рост числа сообщений/пользователей** → SQLite легко тянет тысячи записей; вопрос миграции на Postgres возникнет только при реальном деплое.

## Migration Plan

Greenfield — миграции нет. Единственное: добавить `data/` в `.gitignore`, при старте создавать каталог и схему. Откат — удалить `data/lifekick.db` (потеря истории) и вернуть прежний `bot.py`.
